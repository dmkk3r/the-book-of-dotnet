<Block n={1} title="Das Problem">

Für den GC gibt es normalerweise nur eine Art von Verweis: Ein Feld, eine lokale Variable oder ein statisches Feld zeigt auf ein Objekt, und solange so ein Verweis von einer Root aus erreichbar ist, lebt das Objekt. Diese Regel ist einfach und deckt fast alles ab. An ein paar Stellen reicht sie aber nicht.

**Festhalten ohne verwalteten Verweis.** Übergibst du einer nativen Bibliothek einen Callback samt Zustandsobjekt, merkt sich die Bibliothek nur eine Zahl. Im verwalteten Code zeigt vielleicht nichts mehr auf das Zustandsobjekt. Der GC würde es einsammeln, und der nächste Callback liefe ins Leere. Es braucht also einen Weg, ein Objekt ausdrücklich am Leben zu halten, ohne dass ein Feld darauf zeigt.

**Beobachten ohne festzuhalten.** Ein Cache möchte ein teuer berechnetes Objekt wiederverwenden, solange es ohnehin noch lebt, aber nicht der Grund sein, dass es lebt. Ein normaler Verweis kann das nicht, jeder Verweis hält fest.

**Nicht verschieben.** Nativer Code arbeitet mit Adressen. Verschiebt der GC beim Kompaktieren ein Array, während eine native Funktion hineinschreibt, schreibt sie an die alte Stelle.

**Daten an fremde Objekte hängen.** Ein Framework will zu beliebigen Objekten Zusatzinformationen speichern, ohne deren Klassen zu ändern und ohne sie dadurch unsterblich zu machen.

All diese Fälle löst die Runtime mit demselben Werkzeug: **GC-Handles**. Ein Handle ist ein Eintrag in einer Tabelle, die der GC kennt und bei jeder Collection nach den Regeln des jeweiligen Handle-Typs behandelt.

</Block>

<Block n={2} title="Das mentale Modell">

Die Runtime führt eine **Handle-Tabelle**, getrennt vom verwalteten Heap. Jeder Eintrag zeigt auf ein Objekt und hat einen Typ, der festlegt, wie der GC ihn behandelt:

1. **Normal** (stark): Der Eintrag ist eine Root. Das Objekt lebt, bis das Handle freigegeben wird.
2. **Weak** (kurz schwach): Keine Root. Ist das Objekt sonst unerreichbar, setzt der GC das Handle auf `null`, und zwar noch bevor ein Finalizer laufen könnte.
3. **WeakTrackResurrection** (lang schwach): Keine Root. Wird erst geleert, wenn das Objekt nach der Finalisierung wirklich tot ist.
4. **Pinned**: Eine Root, die das Objekt zusätzlich an seiner Adresse festhält.
5. **Dependent**: Ein Paar aus zwei Objekten. Das erste wird schwach gehalten, das zweite lebt genau so lange wie das erste.

`GCHandle` ist die öffentliche API dafür: `GCHandle.Alloc(obj, type)` legt einen Eintrag an, `Target` liest das Ziel, `Free` gibt den Eintrag frei. `WeakReference` und `WeakReference<T>` sind Klassen, die intern ein Weak-Handle besitzen, `ConditionalWeakTable` baut auf Dependent-Handles auf.

Wo die Handles im Ablauf einer Collection auftauchen, steht im Book of the Runtime: Starke Handles werden wie andere Roots beim Markieren berücksichtigt, schwache Handles behandelt der GC nach dem Markieren und leert die, deren Ziel unmarkiert geblieben ist.

<Block n={4} title="Die Handle-Typen im Detail">

### GCHandle

`GCHandle` ist ein Werttyp, der eine Kennung des Tabelleneintrags enthält. Er hat keinen Finalizer und gibt nichts von selbst frei: Jedes `Alloc` braucht genau ein `Free`. Nach `Free` ist das Struct ungültig, ein weiterer Zugriff auf `Target` löst eine `InvalidOperationException` aus.

Für nativen Code gibt es `GCHandle.ToIntPtr(handle)`. Das Ergebnis ist eine Zahl, die du als `void*`-Kontext an eine native Bibliothek übergeben kannst. Im Callback machst du daraus mit `GCHandle.FromIntPtr(ptr)` wieder ein Handle und kommst über `Target` an dein Objekt:

```csharp
var state = new CallbackState();
GCHandle handle = GCHandle.Alloc(state);              // Normal: hält state fest
NativeLib.Register(&OnEvent, GCHandle.ToIntPtr(handle));

[UnmanagedCallersOnly]
static void OnEvent(IntPtr context)
{
    var s = (CallbackState)GCHandle.FromIntPtr(context).Target!;
    s.Handle();
}
// beim Abmelden: NativeLib.Unregister(); handle.Free();
```

Wie Funktionszeiger und `UnmanagedCallersOnly` zusammenspielen, zeigt „Funktionszeiger und Callbacks“.

Ein `Pinned`-Handle hält das Objekt zusätzlich an seiner Adresse fest. `AddrOfPinnedObject` liefert dann die Adresse der Daten. Das geht nur für Objekte, deren Inhalt nativer Code direkt lesen kann, also Arrays und Strings aus blittable Elementen oder blittable Klassen, sonst wirft `Alloc` eine `ArgumentException`. Für kurze Aufrufe ist `fixed` die bessere Wahl, weil es kein Handle braucht. Warum langes Pinning den Heap zerstückelt, steht in „Pinning und Fragmentierung“.

### Kurz und lang schwach

Der Unterschied zwischen `Weak` und `WeakTrackResurrection` ergibt sich aus der Reihenfolge, in der der GC beim Markieren vorgeht:

1. Alles markieren, was von starken Roots aus erreichbar ist.
2. **Kurze schwache Handles** leeren, deren Ziel unmarkiert ist.
3. Die Finalization Queue durchsuchen, unerreichbare Objekte mit Finalizer in die F-Reachable Queue verschieben und von dort aus erneut markieren.
4. **Lange schwache Handles** leeren, deren Ziel immer noch unmarkiert ist.

{/* TODO(verify): This order against gc.cpp mark_phase (GcShortWeakPtrScan, ScanForFinalization, scan of dependent handles, GcWeakPtrScan). */}

Ein Objekt mit Finalizer, das auf seinen Finalizer wartet, ist für ein kurzes Handle also schon tot, für ein langes noch lebendig. Das ist Absicht: Der Finalizer könnte das Objekt wiederbeleben (siehe „Finalisierung“). Ein kurzes Handle zeigt danach trotzdem auf `null`, ein langes auf das wiederbelebte Objekt. In der Praxis willst du fast immer das kurze: Ein Objekt nach seinem Finalizer weiterzubenutzen, ist selten sinnvoll, denn es hat seine Ressourcen ja schon freigegeben. `new WeakReference(obj)` erzeugt ein kurzes, `new WeakReference(obj, trackResurrection: true)` ein langes Handle.

### WeakReference und WeakReference&lt;T&gt;

`WeakReference<T>` ist die empfohlene, typsichere Variante. Sie hat bewusst keine `IsAlive`-Eigenschaft, sondern nur `TryGetTarget(out T target)`, die das Ziel in einem Schritt prüft und liefert. Warum das wichtig ist, zeigt die Stolperfalle weiter unten.

Jedes `WeakReference` kostet zwei Dinge: ein kleines Objekt auf dem Heap und einen Eintrag in der Handle-Tabelle. Den Eintrag gibt die Runtime frei, wenn das `WeakReference`-Objekt selbst eingesammelt wird. Wer Millionen schwacher Verweise anlegt, hat also Millionen Handles, und die muss der GC bei Collections durchgehen.

<Block n={5} title="ConditionalWeakTable und Dependent-Handles">

### Warum ein Dictionary nicht reicht

Angenommen, du willst zu beliebigen Objekten Zusatzdaten speichern, etwa ein Serialisierer, der pro Objekt einen Zustand merkt. Mit einem `Dictionary<object, Meta>` hält das Wörterbuch jeden Schlüssel stark fest. Kein Objekt, das je hineingekommen ist, stirbt, solange das Wörterbuch lebt.

Der naheliegende Ausweg, die Schlüssel als `WeakReference` zu speichern, scheitert an einem Detail: Die Werte sind weiterhin stark gehalten. Zeigt ein Wert auf seinen Schlüssel, und bei angehängten Zusatzdaten ist das sehr häufig, hält der Wert den Schlüssel am Leben und damit indirekt sich selbst. Das schwache Handle wird nie geleert.

### Was ein Dependent-Handle anders macht

Ein **Dependent-Handle** verbindet ein primäres und ein sekundäres Objekt. Das primäre wird nicht festgehalten. Das sekundäre lebt genau so lange, wie das primäre aus einem anderen Grund lebt. Der GC behandelt das Paar so, als hätte das primäre Objekt ein unsichtbares Feld, das auf das sekundäre zeigt. Ein Verweis vom Wert zurück auf den Schlüssel erzeugt deshalb keinen Kreislauf, der etwas am Leben hält.

<StepPlayer script={cwtScript} />

Für den GC ist das aufwendiger als ein normales Handle. Ob ein sekundäres Objekt lebt, hängt davon ab, ob sein primäres markiert ist, und das kann wiederum von anderen sekundären Objekten abhängen. Der GC muss die Dependent-Handles deshalb wiederholt durchgehen, bis sich nichts mehr ändert.

{/* TODO(verify): Iterative scanning of dependent handles until no new objects are promoted (gc.cpp scan_dependent_handles / GcDhReScan) and its cost with many entries. */}

`ConditionalWeakTable<TKey, TValue>` verpackt das in eine bequeme API. Sie vergleicht Schlüssel nach Referenzidentität, nicht nach `Equals`, ist threadsicher und hält ihre Schlüssel nicht fest. Typische Methoden sind `Add`, `TryGetValue`, `GetValue(key, createValueCallback)` und `AddOrUpdate`. Seit .NET 6 gibt es das zugrunde liegende `DependentHandle` auch als öffentlichen Typ.

<Block n={6} title="Stolperfallen">

### IsAlive prüfen, dann Target lesen

Zwischen zwei Zeilen Code kann jederzeit eine Collection stattfinden, ausgelöst von einer Allokation auf irgendeinem Thread. Wer erst `IsAlive` fragt und dann `Target` liest, prüft etwas, das im nächsten Moment nicht mehr stimmt.

<StepPlayer script={raceScript} />

Die Lösung ist einfach: Ziel einmal in eine lokale Variable lesen und nur diese prüfen. Eine lokale Variable ist eine starke Root, das Objekt kann dir also nicht mehr unter den Händen verschwinden.

```csharp
if (cacheRef.TryGetTarget(out var data))   // WeakReference<T>
    data.Use();

var obj = weakRef.Target as Data;          // WeakReference
if (obj is not null) obj.Use();
```

`IsAlive` taugt nur für die umgekehrte Aussage: `false` bleibt `false`, ein toter schwacher Verweis wird nie wieder lebendig.

### Caches aus schwachen Verweisen

Ein Cache, der seine Einträge nur über `WeakReference` hält, wirkt elegant: Der GC räumt auf, sobald niemand die Einträge braucht. In der Praxis ist er fast leer. Neue Einträge liegen in Gen0, und die nächste Gen0-Collection, die oft nur Millisekunden später kommt, leert jedes Handle, dessen Ziel sonst niemand hält. Der Cache trifft also nur dann, wenn das Objekt ohnehin noch anderswo festgehalten wird. Außerdem hängt seine Trefferquote von Allokationsrate und GC-Modus ab, nicht von deiner Anwendung.

### GCHandle.Free vergessen

Ein `Normal`- oder `Pinned`-Handle ohne `Free` ist ein Speicherleck. Bei `Pinned` kommt Fragmentierung dazu, weil der GC um das festgehaltene Objekt herum nicht kompaktieren kann. Kapsle die Lebensdauer eines Handles deshalb in einen Typ mit `Dispose` und gib es auf jedem Weg frei, auch bei Ausnahmen. Im Speicherabbild zeigt SOS mit `!gchandles` die Handles nach Typ, mit `!gcroot` siehst du, wenn ein Objekt nur über ein Handle lebt.

{/* TODO(verify): SOS command names and output (!gchandles statistics per handle type, !gcroot showing "HandleTable" roots). */}

### Ereignisse halten Abonnenten fest

Das häufigste Leck dieser Art hat gar nichts mit Handles zu tun. Abonniert ein kurzlebiges Objekt ein Ereignis eines langlebigen, speichert der Delegate im Ereignis einen starken Verweis auf den Abonnenten. Der Abonnent lebt dann so lange wie der Herausgeber. Die erste Antwort ist, sich ordentlich abzumelden, etwa in `Dispose`. Wo das nicht möglich ist, helfen schwache Ereignismuster: Der Herausgeber hält seine Abonnenten über schwache Verweise, wie es etwa der `WeakEventManager` in WPF tut. Dafür muss er tote Einträge selbst aufräumen, und Lambdas, die nur der Delegate festhält, sterben sofort.

</Block>

<Block n={7} title="In der Praxis">

### Welches Werkzeug wofür

| Typ                     | Root?           | Wann geleert oder frei                           | Typischer Einsatz                                       |
| ----------------------- | --------------- | ------------------------------------------------ | ------------------------------------------------------- |
| `Normal`                | ja              | bei `Free`                                       | Zustandsobjekt für native Callbacks                     |
| `Pinned`                | ja, und fixiert | bei `Free`                                       | Puffer, den nativer Code länger benutzt                 |
| `Weak`                  | nein            | wenn das Ziel unerreichbar ist, vor Finalizern   | `WeakReference`, Beobachter, Ereignismuster             |
| `WeakTrackResurrection` | nein            | erst nach der Finalisierung                      | selten, wenn auch wiederbelebte Objekte zählen sollen   |
| Dependent               | nein            | wenn der Schlüssel stirbt, samt Wert             | `ConditionalWeakTable`, Daten an fremde Objekte hängen  |

### Caches richtig bauen

Für Caches nimm einen Cache mit klarer Verdrängungsstrategie, etwa `MemoryCache` aus `Microsoft.Extensions.Caching.Memory`. Er hält Einträge stark, verdrängt sie aber nach Ablaufzeit, nach Größe oder bei Bedarf. Damit bestimmst du, wie lange etwas lebt, und nicht der Zufall der nächsten Collection. Bedenke dabei die Midlife Crisis aus „Generationen“: Einträge mit kurzer Ablaufzeit erreichen oft Gen2 und sterben dort.

### Kosten im Blick

Handles sind billig, aber nicht kostenlos. Jedes Handle ist ein Eintrag, den der GC bei Collections prüfen muss, Dependent-Handles sogar wiederholt. Ein paar Tausend sind unproblematisch, Millionen kurzlebiger `WeakReference`-Objekte können GC-Pausen messbar verlängern. In einem GC-Trace siehst du die Zahl der Handles pro Collection, im Speicherabbild die Verteilung nach Typ.

<Block n={8} title="Was Runtime und JIT dazu tun">

Sie ist in Abschnitte nach Handle-Typ gegliedert und merkt sich für ihre Einträge ein Alter, damit eine Gen0-Collection nicht jedes Handle im Prozess anschauen muss, sondern vor allem die, deren Ziel in den eingesammelten Generationen liegen kann. Beim Kompaktieren aktualisiert der GC die Einträge wie jeden anderen Verweis, mit Ausnahme gepinnter Ziele, die sich nicht bewegen.

<Block n={11} title="Das Wichtigste in Kürze">

- **GC-Handles** sind Einträge in einer Tabelle der Runtime, die der GC je nach Typ als Root behandelt oder nicht.
- **Normal** und **Pinned** halten ihr Ziel fest, Pinned zusätzlich an seiner Adresse. Jedes `GCHandle.Alloc` braucht ein `Free`, sonst entsteht ein Leck.
- **Weak** wird geleert, sobald das Ziel unerreichbar ist, noch vor der Finalisierung. **WeakTrackResurrection** erst danach.
- `WeakReference` hält nichts fest und wartet nicht auf Speicherdruck. Caches aus schwachen Verweisen leeren sich bei jeder Gen0-Collection, nimm `MemoryCache`.
- Ziel eines schwachen Verweises **einmal lesen**, dann prüfen. `IsAlive` gefolgt von `Target` ist ein Wettlauf.
- **Dependent-Handles** halten einen Wert genau so lange wie seinen Schlüssel. `ConditionalWeakTable` hängt damit Daten an Objekte, ohne Leck, auch wenn der Wert auf den Schlüssel zeigt.
- Handles kosten GC-Zeit. Millionen davon, besonders Dependent-Handles, verlängern Collections.

</Block>
