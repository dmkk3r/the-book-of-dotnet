<Block n={1} title="Das Problem">

Diese Plattform erklärt dir mentale Modelle der Runtime: wie ein Host die Version wählt, wie die Runtime startet, wie ein Typ geladen wird. Jedes Modell ist eine Vereinfachung, und jede Vereinfachung kann an der entscheidenden Stelle falsch sein. Dokumentation veraltet, Blogposts beziehen sich auf eine Version von vor drei Jahren, und Antworten in Foren wiederholen oft, was vor .NET Core galt. Irgendwann stehst du vor einer Frage, die keine dieser Quellen sicher beantwortet: Wirft diese Methode hier wirklich? Alloziert sie? Was macht `GC.Collect()` eigentlich, bevor der GC anfängt?

Die letzte Instanz ist der Quellcode. .NET ist seit Jahren quelloffen, und fast alles, was in dieser Plattform beschrieben wird, liegt in einem einzigen Repository: **dotnet/runtime** auf GitHub. Darin stecken die Runtime CoreCLR mit VM, JIT und GC, die komplette Klassenbibliothek, die Host-Komponenten, die zweite Runtime Mono und die Design-Dokumente des .NET-Teams, darunter das Book of the Runtime.

Das Problem ist die Größe. Das Repo enthält Millionen Zeilen C# und C++, und wer es zum ersten Mal öffnet, sieht hunderte Ordner ohne erkennbare Ordnung. Dazu kommen zwei Fallen, die selbst erfahrene Entwickler regelmäßig erwischen: Die Grenze zwischen C# und C++ verläuft nicht dort, wo man sie vermutet, und der Code auf der Startseite ist nicht der Code, der auf deinem Rechner läuft.

Diese Lektion gibt dir eine Landkarte, zeigt die Übergänge zwischen verwaltetem und nativem Code und spielt eine Suche von einer öffentlichen API bis in den GC einmal vollständig durch. Bauen musst du dafür nichts. Lesen reicht.

</Block>

<Block n={2} title="Das mentale Modell">

Fünf Sätze tragen das Modell:

1. **Ein Repo, drei große Teile.** Laut Workflow-Dokumentation besteht dotnet/runtime aus den Runtimes (CoreCLR und Mono), den Bibliotheken und den Hosts mit Installern. Jeder Teil hat seinen eigenen Bereich unter `src/`.
2. **Die meiste Klassenbibliothek ist C#.** Auch `System.Private.CoreLib` ist überwiegend verwalteter Code. Nur an wenigen, klar markierten Stellen ruft sie in die Runtime.
3. **Übergänge sind markiert.** Ein Aufruf aus C# in die Runtime ist entweder ein **FCall** (`extern` mit `MethodImplOptions.InternalCall`) oder ein **QCall** (ein P/Invoke auf die Pseudobibliothek `"QCall"`). Jede dieser Markierungen führt über einen Namen zu genau einer C++-Funktion.
4. **Ein Name ist der Suchschlüssel.** Methodenname, `EntryPoint`, Eintrag in einer Tabelle: Wer den richtigen Bezeichner kopiert und sucht, folgt dem Aufruf durch alle Schichten.
5. **Die Version entscheidet.** Lies den Stand, der zu deiner Runtime passt: einen Tag wie `v9.0.0` oder den Zweig `release/9.0`. `main` ist die nächste Version, die es noch nicht gibt.

<Callout kind="fehlannahme">
  „Die Klassenbibliothek ist in C++ geschrieben, C# ist nur eine dünne Hülle.“ Nein: `List<T>`,
  `Dictionary<TKey, TValue>`, `string.Split`, LINQ, `HttpClient` und der größte Teil von CoreLib
  sind C#. Nativer Code beginnt erst an markierten Übergängen, und das .NET-Team verschiebt seit
  Jahren Code aus C++ nach C#, weil der JIT verwalteten Code gut optimiert und er sicherer zu
  schreiben ist.
</Callout>

### Eine CoreLib aus drei Quellen

`System.Private.CoreLib` liegt nicht an einer Stelle. Der größte Teil, etwa `String.cs`, `Object.cs` oder `List.cs`, steht unter `src/libraries/System.Private.CoreLib/src/` und wird von allen drei Runtimes geteilt. Was nur für eine Runtime gilt, steht in deren Ordner und ergänzt die gemeinsame Klasse als `partial class`: `src/coreclr/System.Private.CoreLib/` für CoreCLR, `src/mono/System.Private.CoreLib/` für Mono, `src/coreclr/nativeaot/System.Private.CoreLib/` für Native AOT.

Am Beispiel `GC`: Die gemeinsame Datei ist `GC.cs`, dazu kommen `GC.CoreCLR.cs`, `GC.Mono.cs` und `GC.NativeAot.cs`. Die Endung im Dateinamen sagt dir sofort, für welche Runtime ein Stück Code gilt. Wenn du verstehen willst, was auf einem normalen Desktop- oder Serverprozess passiert, ist die Variante `.CoreCLR.cs` die richtige.

### Klassenbibliothek: ref, src, tests

Jede andere Assembly hat unter `src/libraries/` einen eigenen Ordner mit ihrem Namen, etwa `System.Collections/`. Darin gibt es fast immer drei Unterordner: `ref/` mit dem Quelltext der **Referenzassembly**, also nur der öffentlichen Signaturen, `src/` mit der Implementierung und `tests/` mit den Unit-Tests. Die Datei `src/libraries/System.Runtime/ref/System.Runtime.cs` ist damit die lesbarste Beschreibung der öffentlichen API von `System.Runtime`, gegen die dein Code kompiliert wird.

### Wo der Host liegt

Die Host-Komponenten aus „Der Host: dotnet, hostfxr, hostpolicy“ liegen unter `src/native/corehost/`, mit Unterordnern wie `fxr/`, `apphost/` und `dotnet/`. Das war nicht immer so: Bis .NET 5 lag derselbe Code unter `src/installer/corehost/`. Wer einen älteren Blogpost liest, findet deshalb Pfade, die es heute nicht mehr gibt.

### Die Dokumentation im Repo

Unter `docs/design/` liegen die Design-Dokumente. `docs/design/coreclr/botr/` ist das **Book of the Runtime** (BOTR), eine Sammlung von Kapiteln, in denen Entwickler der Runtime einzelne Teile erklären: Typsystem, GC, Typlader, Threading, CoreLib. `docs/design/features/` beschreibt einzelne Funktionen, etwa die Host-Komponenten, die Auflösung von Framework-Versionen oder die Konfliktauflösung zwischen App- und Framework-Assemblies. `docs/workflow/` erklärt Bauen, Testen und Debuggen. `docs/project/glossary.md` übersetzt die vielen Abkürzungen, auf die du im Code stößt.

<Block n={5} title="Wo verwalteter und nativer Code sich treffen">

### Warum es Übergänge braucht

CoreLib ist eng mit der VM verwoben. Manches kann C# nicht selbst: ein Objekt im GC-Heap anlegen, eine Sammlung auslösen, die MethodTable eines Typs zur Laufzeit befragen. Dafür muss verwalteter Code in die C++-Runtime rufen. Das Book of the Runtime beschreibt in seinem Kapitel über CoreLib zwei Wege dafür, und beide sind im Quelltext eindeutig erkennbar.

### QCall: ein P/Invoke in die Runtime

Ein **QCall** ist im Kern ein gewöhnlicher P/Invoke. Er wird in C# mit `LibraryImport` (früher `DllImport`) deklariert, nennt als Bibliothek aber die Konstante `RuntimeHelpers.QCall` mit dem Wert `"QCall"`. Die Runtime lädt dafür keine Datei, sondern schaut in eine eingebaute Tabelle. Argumente werden wie bei jedem P/Invoke in native Typen umgewandelt, und der Thread wechselt in den **präemptiven** Modus, in dem der GC jederzeit laufen darf. Objektverweise reisen nur verpackt über spezielle Handles, etwa `ObjectHandleOnStack`, damit der GC sie sieht.

Laut BOTR sind QCalls der bevorzugte Weg, weil sie schwer falsch zu benutzen sind. Auf der nativen Seite sind sie freie C-Funktionen mit `extern "C"` und `QCALLTYPE`, eingerahmt von `BEGIN_QCALL` und `END_QCALL`. Gefunden werden sie über ihren Namen: In .NET 8, 9 und 10 steht jeder QCall als `DllImportEntry(Name)` in `src/coreclr/vm/qcallentrypoints.cpp`.

### FCall: direkt in die VM

Ein **FCall** ist älter und direkter. In C# ist er eine `extern`-Methode mit `[MethodImpl(MethodImplOptions.InternalCall)]`, ohne Rumpf und ohne Bibliotheksnamen. Der Aufruf springt ohne Umwandlung und ohne Moduswechsel in eine C++-Funktion, die mit Makros wie `FCIMPL1` definiert ist. Objekte kommen als rohe Zeiger an.

Das ist schnell, aber gefährlich. Der Thread bleibt im kooperativen Modus, der GC kann also nicht nebenher laufen, und wenn die Funktion doch etwas tut, das einen GC auslöst, muss sie vorher von Hand einen Frame aufbauen und ihre Objektverweise schützen. Vergisst sie das, zeigen die Verweise nach dem GC auf alte Adressen. Das BOTR nennt so etwas ein **GC-Loch** und empfiehlt FCalls nur noch für sehr kurze, häufige Wege, die weder allozieren noch Locks nehmen noch werfen.

### Intrinsics: weder noch

Es gibt einen dritten Fall, der beim Lesen verwirrt. Manche Methoden tragen `[Intrinsic]`. Das heißt: Der JIT kennt sie beim Namen und darf ihren Aufruf durch eigenen Code ersetzen. `string.Length` ist so ein Fall. Im Quelltext ist der Getter eine Zeile C#, die das Feld `_stringLength` liest, und der JIT erkennt ihn als `NI_System_String_get_Length`, kann ihn bei einem konstanten String sogar durch die Zahl ersetzen. Einen Übergang in C++ gibt es hier gar nicht. Willst du wissen, was der JIT mit einem Intrinsic macht, suchst du den Namen im Ordner `src/coreclr/jit/`.

### Und der Rest der Bibliothek?

Assemblies außerhalb von CoreLib dürfen weder FCalls noch QCalls benutzen, die Runtime prüft das. Brauchen sie das Betriebssystem, gehen sie über ganz normale P/Invokes: unter Windows direkt in Systembibliotheken, unter Unix meist in die Hilfsbibliothek `System.Native`, deren C-Quelltext unter `src/native/libs/` liegt. Die C#-Seite dieser Aufrufe liegt in Klassen namens `Interop` mit Unterklassen wie `Interop.Sys`, die meist in Dateien unter `src/libraries/Common/src/Interop/` stehen.

<Block n={6} title="Stolperfallen">

### main ist nicht deine Version

Die Startseite von dotnet/runtime zeigt den Zweig `main`. Dort entsteht die nächste Hauptversion, und dort wird kräftig umgebaut. Das Beispiel oben ist kein Sonderfall: Zwischen zwei Versionen wandern FCalls nach C#, Tabellen werden zusammengelegt, Dateien umbenannt. Wer mit .NET 9 arbeitet und auf `main` liest, sieht womöglich Verhalten, das sein Prozess gar nicht hat.

Jede veröffentlichte Version hat einen **Tag** im Repo, etwa `v8.0.0`, `v9.0.0` oder `v10.0.0`, und jede Hauptversion einen Zweig `release/8.0`, `release/9.0` und so weiter, in dem die Patches entstehen. Auf GitHub wählst du ihn über das Auswahlfeld für Zweige und Tags, oder du ersetzt `main` in der Adresse durch den Namen. Mit welchem Commit deine installierte Runtime gebaut wurde, kannst du sogar direkt aus ihr auslesen, wie unten im Abschnitt zum Selbstnachweisen gezeigt.

### Links, die nicht wandern

Ein Link wie `github.com/dotnet/runtime/blob/main/src/coreclr/vm/ecalllist.h` funktioniert heute schon nicht mehr, weil es die Datei auf `main` nicht mehr gibt. Ein Link mit Zeilennummer auf `main` zeigt nach ein paar Wochen auf eine andere Zeile. Wenn du eine Stelle festhalten willst, für ein Ticket, eine Code-Review oder deine eigenen Notizen, verlinke einen Tag oder einen Commit. Auf GitHub erzeugt die Taste `y` aus der aktuellen Ansicht einen **Permalink** mit dem vollständigen Commit-Hash.

### Der Code gilt für eine andere Runtime

Die zweite Falle ist die Dateiendung. `GC.Mono.cs` und `GC.CoreCLR.cs` sehen auf den ersten Blick ähnlich aus, beschreiben aber zwei verschiedene Runtimes. Wer über die Suche auf eine Datei unter `src/mono/` oder `src/coreclr/nativeaot/` stößt, liest Code, der in einer gewöhnlichen Desktop- oder Server-App nicht läuft. Prüf beim ersten Blick auf eine Fundstelle immer den Pfad.

</Block>

### Suchen statt klicken

Drei Werkzeuge decken fast jede Frage ab:

- **source.dot.net** ist ein Quellbrowser über die Klassenbibliothek. Er löst Bezeichner auf wie eine IDE: Klick auf eine Methode führt zur Definition, „Find references“ zu allen Aufrufern. Ideal für den C#-Teil, aber nicht für C++. Achte auf die angezeigte Version.
- **GitHub-Codesuche** im Repo findet Bezeichner in C# und C++ zugleich. Das ist der schnellste Weg über die Sprachgrenze, etwa vom `EntryPoint` eines QCalls zur C++-Funktion.
- **Ein lokaler Klon** mit `git grep` ist am verlässlichsten, weil du gezielt einen Tag auschecken kannst. Laut Workflow-Dokumentation überträgt ein vollständiger Klon rund 400 bis 500 MB. Bauen musst du zum Lesen nicht.

### Tests als Dokumentation

Wenn der Code eine Frage offenlässt, beantworten oft die Tests sie. Für die Bibliothek liegen sie neben dem Code in `src/libraries/<Assembly>/tests/`, für Runtime, JIT und GC unter `src/tests/`. Ein Test zeigt dir ein minimales, lauffähiges Beispiel und das erwartete Ergebnis, und weil er in CI läuft, ist er aktueller als jeder Blogpost. Gerade bei Grenzfällen, etwa was eine Methode bei leerer Eingabe tut, lohnt der Blick dort zuerst.

### Bauen nur bei Bedarf

Wer selbst Änderungen ausprobieren will, baut mit `build.sh` (Linux und macOS) oder `build.cmd` (Windows) im Wurzelordner. Die Workflow-Dokumentation beschreibt die Voraussetzungen je Plattform und die Konfigurationen Debug, Checked (nur CoreCLR, optimiert mit Assertions) und Release. Für alles in dieser Plattform reicht Lesen.

</Block>

<Block n={8} title="Was sich zwischen Versionen ändert">

Der Code der Runtime ist in Bewegung, und die Richtung ist klar: weg von C++, hin zu C#. Das BOTR sagt ausdrücklich, dass Teile der CLR, die stark auf FCalls angewiesen waren, nach verwaltetem Code portiert wurden, etwa Reflection, Teile von Encoding und String-Operationen, und dass das .NET-Team diesen Weg fortsetzen will. `Object.GetType()` ist ein Beispiel aus jüngster Zeit, `GC.Collect()` hat zwischen .NET 9 und 10 einen zusätzlichen Parameter in seinem QCall bekommen.

Auch die Struktur wandert. Der Host zog von `src/installer/` nach `src/native/`, die Tabellen für Übergänge wurden zusammengelegt. Pfade aus dieser Lektion sind deshalb Momentaufnahmen. Was stabil bleibt, ist das Vorgehen: Markierung im C#-Code erkennen, Bezeichner kopieren, im richtigen Stand suchen.

<Callout kind="version">
  Die Beispiele dieser Lektion sind beim Tag `v9.0.0` gelesen, ergänzt um Vergleiche mit
  `release/10.0` und `main` (Stand November 2026). Bei einer anderen Version können Dateinamen,
  Zeilen und Signaturen abweichen. Die Mechanismen FCall und QCall gibt es in allen Versionen seit
  .NET Core.
</Callout>

### Den Weg selbst gehen

Wiederhole das Durchspielen mit einer anderen API, zum Beispiel `GC.GetTotalMemory` oder `GC.GetGeneration`:

```bash
git clone --filter=blob:none https://github.com/dotnet/runtime
cd runtime
git checkout v9.0.0
git grep -n "GCInterface_GetTotalMemory"
git grep -n "\"GetGeneration\"" src/coreclr/vm
```

<Block n={11} title="Das Wichtigste in Kürze">

- **dotnet/runtime** enthält CoreCLR (VM, JIT, GC), Mono, die ganze Klassenbibliothek, die Host-Komponenten und die Design-Dokumente samt Book of the Runtime. Der Quellcode ist die letzte Instanz für jede Frage zur Runtime.
- `src/coreclr/` ist die Runtime, `src/libraries/` die Bibliothek mit `ref/`, `src/` und `tests/` je Assembly, `src/native/corehost/` der Host, `docs/design/` die Dokumentation.
- Die Klassenbibliothek ist **überwiegend C#**. CoreLib besteht aus einem gemeinsamen Teil und runtime-spezifischen Dateien wie `GC.CoreCLR.cs`.
- Übergänge in die Runtime sind markiert: **QCall** als `LibraryImport` auf `"QCall"`, **FCall** als `extern` mit `InternalCall`. `[Intrinsic]` heißt, der JIT darf den Aufruf ersetzen.
- Ein Bezeichner ist der Suchschlüssel: `EntryPoint` oder Methodenname kopieren und über die Sprachgrenze hinweg suchen.
- **main ist nicht deine Version.** Lies den Tag oder `release/x.0` deiner Runtime und verlinke Commits statt `main`.
- Zum Lesen musst du nichts bauen. source.dot.net, GitHub-Suche und `git grep` auf einem Klon reichen.

</Block>
