<Block n={1} title="Das Problem">

Eine Assembly beschreibt ihre Typen als Zeilen in Tabellen: Name, Basistyp, Felder, Methoden, Signaturen. Damit kann eine Runtime aber noch nichts ausführen. Um ein Objekt anzulegen, muss sie wissen, wie groß es ist und an welchem Offset jedes Feld liegt. Um eine virtuelle Methode aufzurufen, braucht sie eine Tabelle mit Methodenzeigern. Um einen Cast zu prüfen, muss sie die Kette der Basistypen und die implementierten Interfaces kennen. All das steht nicht fertig in der Datei, sondern muss aus den Metadaten **berechnet** werden.

Diese Berechnung ist teuer. Ein Feldlayout hängt vom Layout des Basistyps ab, der in einer anderen Assembly liegen kann. Die Methodentabelle übernimmt die Slots der Basisklasse. Generische Typen wie `List<Order>` stehen in keiner Datei, sie entstehen erst aus der Kombination einer Definition mit Typargumenten. Eine durchschnittliche Anwendung zieht über das Framework Zehntausende Typen heran, von denen sie nur einen kleinen Teil wirklich benutzt.

{/* TODO(verify): Order of magnitude of types reachable from a typical app via the shared framework ("Zehntausende"). */}

Würde die Runtime beim Start alles vorbereiten, was erreichbar ist, wäre der Start langsam und der Speicherbedarf hoch, für Typen, die nie gebraucht werden. Die Runtime geht deshalb den umgekehrten Weg: Sie lädt einen Typ **erst, wenn Code ihn wirklich braucht**, und dann genau einmal. Dieser Zielkonflikt zwischen Startzeit und Vorhersehbarkeit prägt alles in dieser Lektion: wann geladen wird, in welcher Reihenfolge, wann der statische Konstruktor läuft und wo Fehler auftauchen.

</Block>

<Block n={2} title="Das mentale Modell">

Wie aus einem Token im IL der Name eines Typs und seiner Assembly wird, beschreibt „Metadatentabellen und Tokens“. Hier geht es darum, was danach passiert. Sechs Sätze tragen das Modell:

1. **Typen werden bei Bedarf geladen.** Eine Assembly zu laden heißt nur, die Datei abzubilden und ihre Metadaten lesbar zu machen. Für einen Typ entsteht erst dann eine Laufzeitstruktur, wenn Code ihn braucht.
2. **Der häufigste Auslöser ist der JIT.** Wenn er eine Methode übersetzt, braucht er die Typen, die darin vorkommen. Weitere Auslöser sind Reflection und das Laden abhängiger Typen.
3. **Erst die Eltern, dann das Kind.** Basistyp und Interfaces werden vor dem Typ selbst geladen, weil seine MethodTable auf ihnen aufbaut.
4. **Das Ergebnis ist eine MethodTable mit EEClass im Loader Heap.** Ein TypeHandle zeigt darauf, und dieselbe Kombination aus Typ und Kontext hat immer dasselbe TypeHandle.
5. **Generische Instanzen entstehen bei Bedarf.** `List<Order>` wird gebaut, wenn es zum ersten Mal gebraucht wird, und danach in einer Tabelle wiedergefunden.
6. **Laden ist nicht Initialisieren.** Der statische Konstruktor läuft später, beim ersten auslösenden Zugriff, nach eigenen Regeln.

Aus Satz 2 folgt eine Eigenschaft, die viele überrascht: Weil der JIT eine Methode vollständig übersetzt, bevor ihre erste Zeile läuft, werden die Typen einer Methode **vor** dieser ersten Zeile geladen, nicht an der Stelle, an der sie im Quelltext stehen.

<Callout kind="fehlannahme">
  „Beim Programmstart werden alle Typen der Anwendung geladen.“ Geladen wird nur, was der Code
  tatsächlich braucht, und erst, wenn er es braucht. Eine Assembly kann vollständig geladen sein,
  ohne dass für einen einzigen ihrer Typen schon eine MethodTable existiert.
</Callout>

</Block>

<Block n={4} title="Was beim Laden entsteht">

### Die Schritte im Überblick

Der Ablauf aus der Visualisierung lässt sich in vier Teile gliedern:

| Schritt | Was passiert | Was dabei schiefgehen kann |
| --- | --- | --- |
| Verweis auflösen | TypeRef bis zur AssemblyRef verfolgen, der aktive `AssemblyLoadContext` lädt die Assembly | Assembly nicht gefunden: `FileNotFoundException` |
| Typ finden | TypeDef per Namensraum und Name suchen, Weiterleitungen über ExportedType folgen | Typ fehlt: `TypeLoadException` |
| Abhängigkeiten laden | Basistyp, Interfaces und Werttypen in Feldern laden | jeder Fehler der Abhängigkeit schlägt auf diesen Typ durch |
| Strukturen bauen | Feldlayout, Methodentabelle, Interface-Map berechnen | ungültiges Layout oder fehlende Interface-Implementierung: `TypeLoadException` |

Der zweite Schritt sucht per Name, nicht per Zeilennummer. Ein TypeRef in deiner Assembly kann gar keine Zeilennummer der fremden Assembly kennen, denn die fremde Assembly kann neu gebaut worden sein. Die Runtime hält dafür pro Modul eine Nachschlagetabelle von Namen auf TypeDef-Zeilen bereit.

{/* TODO(verify): Name lookup per module through the "available class hash" (EEClassHashTable in classhash.h) in CoreCLR. */}

Bei den Abhängigkeiten gibt es einen feinen Unterschied. Ein Feld vom Referenztyp ist für das Layout nur ein Zeiger, seine Größe steht fest, egal welcher Typ dahinter steckt. Ein Feld vom Werttyp dagegen liegt inline im Objekt, und seine Größe muss bekannt sein, bevor das Layout feststeht. Deshalb muss der Loader die Werttypen in Feldern laden, die Referenztypen in Feldern aber nicht vollständig.

{/* TODO(verify): That reference-type field types are not loaded (beyond approximate level) while building the MethodTable, but value-type field types are, per BOTR type-loader.md and methodtablebuilder.cpp. */}

### MethodTable, EEClass und TypeHandle

Das Ergebnis des Ladens kennst du aus „MethodTable und EEClass“: Die **MethodTable** enthält die Daten, die zur Laufzeit ständig gebraucht werden, etwa Basisgröße, Basistyp, Interface-Map und die Slots der virtuellen Methoden. Die **EEClass** enthält die selteneren Daten wie Feldbeschreibungen und den Verweis zurück in die Metadaten. Beide liegen im **Loader Heap**, einem Speicherbereich, den nicht der GC verwaltet, sondern der `AssemblyLoadContext`, in den der Typ geladen wurde.

Zwischen Loader und dem Rest der Runtime vermittelt das **TypeHandle**. Das Book of the Runtime nennt es die universellste Typbezeichnung der CLR: ein Zeiger, der entweder auf eine MethodTable zeigt oder, für Zeiger, ByRefs, Funktionszeiger und generische Typvariablen, auf eine kleinere Struktur namens TypeDesc. Zwei TypeHandles sind genau dann gleich, wenn sie denselben Typ bezeichnen. In verwaltetem Code siehst du es als `RuntimeTypeHandle`, etwa über `typeof(Order).TypeHandle`.

Die Visualisierung zeigt, was nach dem Laden im Speicher liegt, und dass Instanzen nur noch auf das Ergebnis zeigen:

### Generische Instanzen

`List<Order>` hat keine TypeDef-Zeile. In den Metadaten deiner Assembly steht nur eine TypeSpec-Signatur, die die Definition `List<T>` mit dem Argument `Order` kombiniert. Die Runtime baut daraus eine eigene MethodTable, sobald die Instanz gebraucht wird, und legt sie in einer Hashtabelle des zuständigen Moduls ab. Bevor sie eine neue Instanz baut, sieht sie dort nach. So gibt es nie zwei MethodTables für denselben Typ, und der Vergleich von TypeHandles bleibt ein Zeigervergleich.

Alle Instanzen für Referenztypen teilen sich eine EEClass und den Code der kanonischen Form `List<__Canon>`. Instanzen für Werttypen bekommen eine eigene EEClass. Was das für Code und statische Felder bedeutet, erklärt die Lektion „Generics zur Laufzeit“.

</Block>

<Block n={5} title="Ladestufen und Zyklen">

### Warum ein Typ nicht in einem Schritt fertig wird

Die Regel „erst die Eltern“ hat ein Problem. Schau dir diese Deklaration an:

```csharp
public class Order : Entity, IComparable<Order> { /* … */ }
```

Um `Order` zu laden, braucht die Runtime das Interface `IComparable<Order>`. Um diese Instanz zu bauen, braucht sie das Typargument `Order`, das gerade erst geladen wird. Noch deutlicher wird es bei Mustern wie `class Node : Base<Node>` oder bei zwei generischen Typen, die sich gegenseitig als Typargument verwenden. Eine naive Rekursion würde sich hier im Kreis drehen oder, wenn zwei Threads gleichzeitig laden, gegenseitig blockieren.

Der Loader löst das, indem er einen Typ **in Stufen** lädt. In der ersten Stufe dürfen Basistyp und Interfaces nur angenähert sein, die generischen Argumente werden durch etwas ersetzt, das den Zyklus nicht enthält. Später werden die exakten Typen eingesetzt. Ein Typ, der gerade erst die erste Stufe erreicht hat, ist schon sichtbar und kann von anderen Typen als Argument benutzt werden, aber noch nicht verwendet werden, um Code auszuführen.

| Stufe | Bedeutung |
| --- | --- |
| `CLASS_LOAD_BEGIN` | Platzhalter: Der Typ existiert noch nicht. |
| `CLASS_LOAD_APPROXPARENTS` | Die MethodTable existiert, Basistyp und Interfaces haben aber möglicherweise nur angenäherte generische Argumente. |
| `CLASS_LOAD_EXACTPARENTS` | Basistyp und Interfaces sind exakt, die Hierarchie ist bis zu dieser Stufe geladen. |
| `CLASS_DEPENDENCIES_LOADED` | Der Typ und alles, wovon er abhängt, ist geladen. Generische Constraints sind noch nicht geprüft. |
| `CLASS_LOADED` | Abschließende Prüfung, etwa der Constraints. Erst jetzt gilt der Typ als vollständig geladen. |

{/* TODO(verify): Stage names and descriptions taken from src/coreclr/vm/classloadlevel.h (main branch, checked 2026-11); confirm they match .NET 8 and pin the link to a commit. */}

Die letzten beiden Stufen werden für Gruppen voneinander abhängiger Typen gemeinsam erreicht: Ein Typ gilt erst dann als vollständig geladen, wenn auch alle Typen seines Zyklus so weit sind. Für dich als Anwender bleibt das unsichtbar. Es erklärt aber, warum der Loader intern so viel mehr Aufwand treibt, als „lies die Zeile und baue die Struktur“ vermuten lässt, und warum Typladen in der Runtime unter Sperren und mit einer Tabelle laufender Ladevorgänge stattfindet.

<Block n={6} title="Statische Konstruktoren">

### Laden ist nicht Initialisieren

Ein Typ kann einen **Typinitialisierer** haben, im IL eine Methode namens `.cctor`. In C# entsteht sie aus einem statischen Konstruktor und aus allen Initialisierern statischer Felder, die der Compiler davor einfügt. Die `.cctor` läuft nicht beim Laden der Assembly und auch nicht beim Laden des Typs. Wann sie läuft, regelt ECMA-335 in Partition I, Abschnitt 8.9.5, und zwar auf zwei Arten:

| Semantik | Wann die `.cctor` läuft | Wann C# sie wählt |
| --- | --- | --- |
| präzise (ohne `beforefieldinit`) | unmittelbar vor dem ersten Zugriff auf ein statisches Feld, dem ersten Aufruf einer statischen Methode oder dem ersten Aufruf eines Konstruktors | die Klasse hat einen expliziten statischen Konstruktor |
| `beforefieldinit` | spätestens beim ersten Zugriff auf ein statisches Feld, zu einem beliebigen früheren Zeitpunkt erlaubt | die Klasse hat nur Feldinitialisierer, keinen statischen Konstruktor |

Bei Werttypen kommt in der präzisen Semantik noch der erste Aufruf einer Instanzmethode hinzu. Die Runtime garantiert in beiden Fällen, dass die `.cctor` genau einmal läuft, auch wenn mehrere Threads gleichzeitig zugreifen: Die anderen warten, bis die Initialisierung abgeschlossen ist.

{/* TODO(verify): Exact trigger list in ECMA-335 I.8.9.5 (value types: first instance or virtual method call) and the C# rule that beforefieldinit is emitted only without an explicit static constructor. */}

Warum zwei Varianten? Die präzise Semantik ist vorhersagbar, kostet aber: Jeder Zugriff, der die `.cctor` auslösen könnte, braucht im erzeugten Code eine Prüfung, ob der Typ schon initialisiert ist. Mit `beforefieldinit` darf die Runtime die Initialisierung vorziehen, etwa bevor sie eine Methode übersetzt, und kann dann die Prüfungen weglassen. Das ist der Grund, warum ein leerer statischer Konstruktor `static Config() { }` messbar langsamere Zugriffe auf statische Felder zur Folge haben kann.

{/* TODO(verify): Measurable cost of an empty static constructor on static field access in .NET 8 Tier1 code (BenchmarkDotNet), and that the JIT may run beforefieldinit cctors at compile time. */}

### Wenn der Typinitialisierer scheitert

Wirft die `.cctor` eine Ausnahme, verpackt die Runtime sie in eine `TypeInitializationException`. Die Visualisierung zeigt, was danach passiert:

<StepPlayer script={cctorScript} />

Der wichtigste Punkt ist der letzte Schritt vor der Fehlannahme: Ein gescheiterter Typinitialisierer wird **nicht wiederholt**. Der Typ ist für die Lebensdauer seines Kontexts unbrauchbar, in einer normalen Anwendung also bis zum Prozessende. Wer in einem statischen Konstruktor eine Datei liest, eine Verbindung aufbaut oder eine Konfiguration prüft, verwandelt einen vorübergehenden Fehler in einen dauerhaften. Für solche Fälle ist `Lazy<T>` oder eine explizite Initialisierungsmethode die bessere Wahl, denn dort kannst du selbst entscheiden, ob ein zweiter Versuch stattfindet.

</Block>

<Block n={7} title="Stolperfallen">

### Die Ausnahme kommt eine Methode zu früh

Stell dir vor, `Shop.dll` fehlt beim Kunden. Du hast vorsichtig programmiert:

```csharp
static void Bestellen()
{
    try
    {
        var o = new Order(42);
        Console.WriteLine(o.Id);
    }
    catch (FileNotFoundException)
    {
        Console.WriteLine("Shop-Modul fehlt");
    }
}
```

Der `catch`-Block wird nie erreicht. Die `FileNotFoundException` entsteht nicht beim Ausführen von `new Order(42)`, sondern beim **Übersetzen** von `Bestellen`, bevor auch nur der `try`-Block betreten wird. Sie fliegt deshalb im Aufrufer heraus, also an der Stelle, an der `Bestellen()` aufgerufen wird. Das Book of the Runtime beschreibt genau diesen Effekt: Eine `TypeLoadException`, die beim Übersetzen entsteht, kann in der übersetzten Methode selbst nicht gefangen werden.

{/* TODO(verify): That a missing assembly surfaces as FileNotFoundException at the call site of the method being JIT compiled (with Tier0 JIT), with message "Could not load file or assembly 'Shop, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null'". */}

Es kommt noch ungemütlicher. Wenn der JIT `Bestellen` in den Aufrufer **inlined**, verschiebt sich der Ladezeitpunkt in die Übersetzung des Aufrufers, und die Ausnahme erscheint eine Ebene weiter oben. Microsoft Learn sagt deshalb ausdrücklich, dass der genaue Zeitpunkt, zu dem statische Assembly-Verweise geladen werden, nicht festgelegt ist und von Optimierungen wie Inlining abhängt. Der robuste Ausweg ist, den Code mit der riskanten Abhängigkeit in eine eigene Methode auszulagern, sie mit `[MethodImpl(MethodImplOptions.NoInlining)]` zu markieren und den `try` um ihren **Aufruf** zu legen.

### Welcher Fehler was bedeutet

Ladefehler haben verschiedene Typen, und jeder sagt etwas anderes:

| Ausnahme | Typische Ursache |
| --- | --- |
| `FileNotFoundException` | Die Assembly aus der AssemblyRef wurde nicht gefunden. |
| `FileLoadException` | Die Assembly wurde gefunden, ließ sich aber nicht laden, etwa wegen einer unpassenden Version im Kontext. |
| `BadImageFormatException` | Die Datei ist keine gültige Assembly oder passt nicht zur Plattform. |
| `TypeLoadException` | Der Typ fehlt in der Assembly, oder er lässt sich nicht bauen, etwa weil eine Klasse eine neue Interface-Methode nicht implementiert. |
| `MissingMethodException`, `MissingFieldException` | Typ gefunden, aber kein Member mit diesem Namen und dieser Signatur. |
| `TypeInitializationException` | Typ geladen, aber der Typinitialisierer ist gescheitert. Die eigentliche Ursache steht in `InnerException`. |

{/* TODO(verify): FileLoadException for a version lower than requested in the same ALC; TypeLoadException message for a missing interface implementation ("Method 'X' in type 'Y' from assembly 'Z' does not have an implementation"). */}

Die Reihenfolge hilft beim Lesen eines Fehlers. Eine `TypeLoadException` zur Laufzeit bedeutet fast immer, dass die Assembly zur Laufzeit eine andere ist als die, gegen die kompiliert wurde. Den Mechanismus dahinter, die Bindung per Name und Signatur, erklärt „Metadatentabellen und Tokens“.

</Block>

<Block n={8} title="In der Praxis">

| Situation | Was passiert | Warum | Ausweg |
| --- | --- | --- | --- |
| Erster Aufruf einer Methode ist langsam | JIT plus Typladen für alle neuen Typen | Laden ist lazy und passiert beim Übersetzen | ReadyToRun, Aufwärmen beim Start |
| `try` fängt `FileNotFoundException` nicht | Ausnahme beim Übersetzen der Methode | Typen werden vor der ersten Zeile geladen | riskanten Code in eigene `NoInlining`-Methode auslagern |
| Ein statischer Wert bleibt für immer kaputt | jeder Zugriff wirft `TypeInitializationException` | gescheiterte `.cctor` wird nicht wiederholt | keine I/O in statischen Konstruktoren, `Lazy<T>` |
| Leerer statischer Konstruktor kostet | Prüfungen vor Feldzugriffen | präzise Semantik statt `beforefieldinit` | statischen Konstruktor weglassen, wenn die Reihenfolge egal ist |
| Viele `MakeGenericType`-Aufrufe | Speicher im Loader Heap wächst | jede neue Instanz ist eine eigene MethodTable | Typen cachen, entladbare Kontexte |
| Zwei Threads benutzen sich gegenseitig in statischen Konstruktoren | Deadlock beim Start | jede `.cctor` läuft unter einer Sperre | Abhängigkeiten zwischen Typinitialisierern vermeiden |

<Block n={9} title="Was Runtime und JIT dazu tun">

**Tiered Compilation** ändert am Prinzip nichts, verschiebt aber die Arbeit. Auch der schnelle Tier-0-Code muss Typen auflösen, also wird beim ersten Aufruf geladen wie beschrieben. Wenn eine Methode später mit Tier 1 neu übersetzt wird, sind ihre Typen bereits geladen und oft auch initialisiert. Dann kann der JIT zum Beispiel den Wert eines `static readonly`-Felds als Konstante einsetzen, weil der Typinitialisierer schon gelaufen ist. Mehr dazu in „Tiered Compilation und OSR“.

{/* TODO(verify): That Tier1 treats static readonly fields of already initialized classes as JIT-time constants (.NET Core 3.0 and later). */}

**ReadyToRun** liefert vorkompilierten Code mit. Dieser Code enthält keine fertigen MethodTable-Adressen, sondern Verweise, die beim ersten Gebrauch aufgelöst werden. Die Typen werden also auch hier bei Bedarf geladen, nur ohne JIT. Der genaue Zeitpunkt kann sich deshalb vom JIT-Fall unterscheiden.

{/* TODO(verify): ReadyToRun fixups are resolved lazily (per call site or per method entry), and how this shifts the point where load errors surface. */}

**Native AOT** geht den entgegengesetzten Weg: Der Compiler baut alle Typstrukturen schon beim Veröffentlichen, zur Laufzeit gibt es keinen Type Loader im beschriebenen Sinn. Deshalb funktionieren dort nur Typen, die der Compiler vorhersehen konnte, ein `MakeGenericType` mit unbekannten Argumenten kann fehlschlagen. Das vertieft „Native AOT“.

  Die Ladestufen und die Trennung von MethodTable und EEClass sind seit Langem stabil. Geändert hat
  sich in den letzten Versionen vor allem, wann Typinitialisierer laufen: Seit Tiered Compilation
  kann die Initialisierung bei `beforefieldinit`-Typen später stattfinden als früher, aber nie
  später als beim ersten Zugriff auf ein statisches Feld.
</Callout>

<Block n={12} title="Das Wichtigste in Kürze">

- Typen werden **bei Bedarf** geladen, meist wenn der JIT eine Methode übersetzt, die sie benutzt. Eine geladene Assembly heißt noch nicht, dass ihre Typen geladen sind.
- Der Ablauf: TypeRef auflösen, Assembly über den aktiven `AssemblyLoadContext` laden, TypeDef per Name finden, **Basistyp und Interfaces zuerst** laden, dann MethodTable und EEClass im Loader Heap bauen.
- Das **TypeHandle** bezeichnet einen geladenen Typ eindeutig. Generische Instanzen wie `List<Order>` entstehen bei Bedarf und werden in einer Tabelle wiedergefunden.
- **Ladestufen** von `CLASS_LOAD_BEGIN` bis `CLASS_LOADED` erlauben zyklische Abhängigkeiten ohne endlose Rekursion.
- **Laden ist nicht Initialisieren.** Die `.cctor` läuft beim ersten auslösenden Zugriff: präzise mit explizitem statischem Konstruktor, mit `beforefieldinit` dagegen zu einem beliebigen Zeitpunkt bis spätestens zum ersten Feldzugriff.
- Ein gescheiterter Typinitialisierer wird **nie wiederholt**, jeder weitere Zugriff wirft `TypeInitializationException`.
- Ladefehler entstehen **beim Übersetzen** der Methode, die den Typ benutzt, und tauchen deshalb im Aufrufer auf, nicht im `try` der Methode selbst.

</Block>
